## ADR-001 비즈니스 로직 없는 3-Depth 호출 체인을 측정 대상으로 한다

**상황:** 기존 연구는 단일 홉 측정이 많아, 호출이 이어질 때 인증 비용이 어떻게 쌓이는지 알 수 없었습니다([PROBLEM_DEFINITION.md](./PROBLEM_DEFINITION.md#2-문제)).

**결정:** Gateway → Order → Inventory → User의 4개 서비스, 내부 3구간 체인을 만듭니다. 각 서비스는 다음 서비스를 부르고 응답에 자기 정보를 붙이기만 합니다.

**결과:**
- 인증 비용 외의 변수(DB, 연산)가 없어 차이가 인증 방식에서 온다고 볼 수 있습니다.
- 대가: 실제 서비스보다 인증 비용의 비중이 크게 나옵니다. 절대값을 실제 서비스에 그대로 옮기면 안 됩니다.

## ADR-002 코드는 하나로 두고 `APP_MODE` 프로파일로 인증 조건을 바꾼다

**상황:** 조건마다 다른 코드를 쓰면 측정 차이가 인증 때문인지 코드 차이 때문인지 구분할 수 없습니다.

**결정:** `APP_MODE`를 Spring 프로파일로 씁니다. `no-auth`는 Security 자동 구성을 빼고, `jwt-relay`에서만 `@ConditionalOnProperty`로 보안 설정과 릴레이 인터셉터를 켭니다. Step 0·2·3은 같은 `no-auth` 이미지를 쓰고 Istio 설정만 다릅니다.

**결과:**
- 조건 사이에 바뀌는 것은 환경변수 하나와 인프라 설정뿐입니다.
- 대가: `jwt-relay`에서는 Security가 모든 경로에 인증을 요구해 actuator(헬스 체크·메트릭)까지 막힙니다([VERIFICATION.md §3](./VERIFICATION.md#3-알려진-문제)).

## ADR-003 JWT는 HS256 공유 비밀키로 검증한다

**상황:** 모든 서비스가 같은 토큰을 각자 검증해야 합니다.

**결정:** HS256(HMAC-SHA256)을 쓰고, 모든 서비스가 같은 `JWT_SECRET`을 읽습니다. 검증은 Spring Security `NimbusJwtDecoder.withSecretKey`, 발급은 `benchmark-tools`(JJWT)가 합니다.

**결과:**
- 키 배포 서버(JWKS)나 토큰 발급 서버 없이 실험을 구성할 수 있습니다. 검증 중 네트워크 호출도 없습니다.
- 대가: 비밀키를 가진 서비스는 누구나 토큰을 만들 수 있어 운영 환경에는 맞지 않습니다. RS256·ES256처럼 비대칭 서명을 쓰면 검증 비용이 달라지므로, 이 결과를 다른 알고리즘에 일반화할 수 없습니다.

## ADR-004 토큰 릴레이는 Feign 인터셉터로 한다

**상황:** 받은 토큰을 다음 서비스 호출에 실어야 합니다. 컨트롤러마다 헤더를 넘기면 코드가 조건별로 달라집니다.

**결정:** `FeignAuthorizationRelayInterceptor`(Feign `RequestInterceptor`)가 현재 요청의 `Authorization` 헤더를 꺼내 모든 Feign 호출에 붙입니다. `jwt-relay`에서만 빈으로 등록됩니다.

**결과:**
- 컨트롤러와 Feign 클라이언트 코드는 조건과 무관하게 같습니다.
- 대가: `RequestContextHolder`(요청 스레드)에 기대므로, 비동기 호출이나 다른 스레드에서 Feign을 부르면 헤더가 전달되지 않습니다. 이 체인은 동기 호출만 씁니다.

## ADR-005 Sidecar Only 단계를 따로 둬 프록시 비용과 mTLS 비용을 나눈다

**상황:** Istio mTLS 결과만 보면 지연이 사이드카를 거쳐서 생긴 것인지, 암복호화 때문인지 알 수 없습니다.

**결정:** 사이드카는 주입하되 mTLS는 끈 Step 2를 둡니다. Step 2 − Step 0이 프록시 비용, Step 3 − Step 2가 순수 mTLS 비용입니다.

**결과:**
- 고부하 기준 순수 mTLS 비용을 약 21ms로 분리했습니다([RESULTS.md §2](./RESULTS.md#2-순수-mtls-오버헤드-step-2-vs-step-3)).
- 대가: Step 2에서 mTLS가 정말 꺼져 있어야 결과가 성립합니다. 당시 Istio 정책 파일이 저장소에 없어 보관이 필요합니다([STATUS.md](./STATUS.md#4-남은-과제)).

## ADR-006 부하·관측·측정 대상을 서로 다른 VM에 둔다

**상황:** JMeter와 Jaeger·Prometheus도 CPU를 많이 씁니다. 같은 노드에 있으면 서비스 CPU 측정이 오염됩니다.

**결정:** VM 3대(각 6 Core / 12GB)를 부하 발생, 컨트롤 플레인·관측, 워커로 나눕니다. 서비스 4개는 `nodeAffinity`로 워커 노드에만 뜨게 합니다.

**결과:**
- 측정 대상 노드에는 서비스와 사이드카만 있습니다.
- 대가: 서비스 4개가 한 노드의 CPU를 나눠 씁니다. 한 서비스가 CPU를 많이 쓰면 다른 서비스 성능도 떨어지므로, 서비스별 CPU는 독립적인 값이 아닙니다.

## ADR-007 대기·웜업·본 측정 3단계와 3회 반복으로 측정한다

**상황:** JVM은 시작 직후 JIT 컴파일로 느리고, Pod 시작 직후에는 컨트롤 플레인 CPU도 튑니다.

**결정:** Startup Wait(1~3분) → Warm-up(10~60초) → Main Test(60초)로 측정하고, 조건마다 3회 반복해 평균에 가장 가까운 회차를 대표로 씁니다([EXPERIMENT_DESIGN.md §5](./EXPERIMENT_DESIGN.md#5-측정-절차)).

**결과:**
- 콜드 스타트와 이상치 한 번의 영향을 줄였습니다.
- 대가: 3회는 통계적 유의성을 따지기에 적습니다. 분산이나 신뢰구간은 내지 않았습니다.

## ADR-008 OTLP + Jaeger로 추적하고, 샘플링은 환경변수로 조정한다

**상황:** 지연이 어느 구간에서 생기는지 보려면 서비스·호출 단위의 시간이 필요합니다.

**결정:** Micrometer Tracing(OpenTelemetry 브리지)으로 스팬을 만들어 OTLP HTTP로 Jaeger에 보냅니다. 수집 주소와 샘플링 비율은 `OTLP_TRACES_ENDPOINT`, `TRACING_SAMPLE_PROBABILITY`로 바꿉니다.

**결과:**
- 코드 수정 없이 추적 대상과 양을 바꿀 수 있습니다.
- 대가: 고부하 측정 중 트레이스가 계속 쌓이며 Jaeger 메모리가 늘어 노드가 멈춘 일이 있었습니다. 기본 샘플링 비율이 1.0(모든 요청)이라 추적량 관리가 필요합니다([RUNBOOK.md RB-01](./RUNBOOK.md#rb-01-jaeger-메모리-증가로-노드가-멈춤)).

## ADR-009 로컬은 Docker Compose, 실험은 Kubernetes로 나눈다

**상황:** 개발 중에는 체인이 동작하는지만 빨리 확인하면 되고, 측정은 Istio가 있는 Kubernetes가 필요합니다.

**결정:** 같은 Dockerfile(`--build-arg SVC=`)로 이미지를 만들고, 로컬은 `docker-compose.yml`(Jaeger 포함), 실험은 `k8s/` 매니페스트로 띄웁니다.

**결과:**
- 노트북에서도 Step 0·1 동작을 바로 확인할 수 있습니다.
- 대가: 설정이 두 군데(compose 환경변수, ConfigMap)에 있어 값을 맞춰야 합니다.

## ADR-010 보안 설정과 Feign 인터셉터를 공통 모듈로 뺀다

**상황:** 4개 서비스가 같은 검증·릴레이 로직을 써야 조건이 공정합니다.

**결정:** `benchmark-common`(속성, 보안 설정)과 `benchmark-feign-common`(인터셉터)을 Maven 모듈로 두고, 각 서비스는 `scanBasePackages = "com.msa.benchmark"`로 가져옵니다.

**결과:**
- 서비스마다 구현이 달라질 여지가 없습니다.
- 대가: 공통 모듈의 빈이 모든 서비스에 들어가므로, 특정 서비스만 다르게 설정하려면 조건을 따로 걸어야 합니다.
